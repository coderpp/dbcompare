# 结构同步、结果报告和注释修复

## 按表选择并生成 SQL

1. 选择源、目标连接和数据库，点击“开始对比”。源定义期望结构，目标接受同步 DDL。
2. 左侧按表勾选，中间展示所选表的字段、索引和属性差异，不再逐个勾选对象。
3. 点击“生成 SQL”。每条语句显示关联的差异，点击关联项可定位到对象。不会按 SQL 顺序猜测差异编号，也不会自动扩大选择范围。
4. 修改选择、连接、数据库或同步选项，会清空旧 SQL，并禁用执行。修改对比选项后需重新开始对比。
5. 右侧支持复制、导出 SQL 文件、导出生成计划时的目标结构快照。SQL 带完整库名和字符集设置；执行前仍需核对实际目标库。

## 是否对比索引

“对比索引”位于“允许删除多余对象”之前，默认勾选；旧方案同样默认开启，设置随方案、执行历史及继续处理保留。

关闭时，对已有表的普通/唯一等索引和主键增删改/重命名不列为差异、不生成对应 SQL，也不计入同步后的剩余差异。字段、外键和其他表属性仍正常对比。只差索引的表会从差异列表消失。

新增整表始终保留源表完整索引和主键定义，删除整表也不受该选项限制。不修改或删除数据库中实际已有的索引来实现“忽略”。

## 执行与报告

执行请求绑定唯一计划编号。执行前重新读取涉及表的 SHOW CREATE TABLE，检查结构是否已变化（普通 AUTO_INCREMENT 计数增长不视为结构变化）。结构变化会拒绝旧计划，要求重新对比。

执行前，目标表快照与完整计划先写入本机 SQLite；保存失败不会开始 DDL。逐条记录 pending → running → success/failed；某条失败后停止，后续语句记为 not_executed。每次执行状态变化都会持久化。使用同一物理连接执行 SQL 及设置/恢复 sql_mode，不禁用外键检查。

执行完成或部分失败后，重新读取两库并使用与手动对比相同的归一化及过滤规则复查：

- **本次所选变更**：按表/字段/索引等对象核对是否仍有差异，不以全库完全相同作为部分同步的成功条件。
- **其他未选差异**：仍在全库报告中列出，不冒充本次执行失败。
- **按选项保留的目标多余对象**：未允许删除时单独标识。
- **复查失败**：保留 SQL 的实际执行结果，同时将复查状态标记为未知。

报告显示成功、失败、未执行、耗时、错误、选择范围、SQL 关联、剩余差异及执行前快照。DDL 自动提交，失败不会自动回滚已经成功的语句。

## 历史与继续处理

顶部“历史与报告 / 乱码修复”中查看执行历史，可重启后打开完整报告。早于本功能的记录可通过“查看旧版逐条日志”查看，不会凭空补造其快照和复查结果。

“重新读取结构，规划剩余项”使用已保存连接重新读取数据库，按表勾选原任务中仍有差异的表；已经成功的 SQL 不会直接重放。需要再次审阅和生成 SQL，再手动确认执行。连接已删除或凭据不可用时，需要先恢复连接。

如果应用在执行中退出，历史可能停在 running/pending。界面会提示执行中或中断，未完成复查的状态显示为未知；不要根据旧状态认定 DDL 未执行，应使用重新读取结构处理。

历史记录剔除连接密码及额外连接参数；密码仍由原有 OS Keychain 管理。历史保存在原有 `dbcompare.sqlite` 中的 `sync_runs` 表。

## 注释乱码检测与修复

1. 先开始对比，确定两库。
2. 打开“乱码检测与修复”，明确选择源库或目标库，再扫描。
3. 预览每个表/字段的原注释和建议恢复内容；可筛选、逐项选择。
4. 点击“生成所选修复 SQL（不执行）”，在主界面检查黄色提示中的**实际目标库**。选择源库修复时，实际修改的是源库。
5. 可以先导出 SQL；也可显式确认执行。修复使用相同的快照、历史、逐条记录和复查流程。

检测将 MySQL Latin1/Windows-1252 错读字符还原为字节，再严格按 UTF-8 解码；只建议增加中文字符的可逆转换，不按字段名猜测注释。正常中文不转换。已丢失字符、不可逆乱码及其他编码损坏不保证检出，必须人工核对。

修复 SQL 根据当前 SHOW CREATE TABLE 保留原字段定义，仅替换 COMMENT；不自动修复业务数据。

## 自动修复乱码注释（0.2.6）

在对比选项中勾选“自动修复乱码注释”（默认关闭），再开始对比。对比只读取数据库，在内存中还原可逆的表/字段注释，并显示两端候选及原文、建议恢复内容；不会自动写库。选项可随方案保存。

生成 SQL 时，会纳入本次对比范围内全部可修复注释，即使未勾选结构差异表也可生成修复计划。源库注释修复和目标库注释修复/结构同步按实际连接、数据库分组预览。确认后先修复源库，再执行目标库计划；任一步失败即停止后续操作，各库执行报告分别保存。已经执行的 DDL 不自动回滚。两个连接指向同一端点同一库时只修复一次。

目标库先执行保留原字段定义的注释修复，再执行基于恢复后模型生成的结构 SQL，避免后续字段变更将乱码写回。不可逆或已丢失的字符不猜测恢复。快照作为源时仅纠正期望模型，不改写快照或其原始数据库。

导出或复制多库 SQL 后，需按分组连接对应服务器执行，不能在单一连接上直接执行整个文件。应用内执行会使用各自的连接。

“执行后自动重新对比”默认勾选并记住选择，完成或部分失败后刷新主界面差异；关闭此选项仍会保留后端执行复查。连接切换时选择新连接的默认库；加载方案、交换两端和快照恢复保留操作指定的数据库。

SQL 复制支持系统剪贴板与浏览器回退，复制失败时可手动选择或导出。手动乱码扫描中也可直接打开修复确认弹窗，查看完整 SQL 后执行。

验证自动修复组合流程：

```sh
DBCOMPARE_TEST_LOCAL=1 go test -tags integration ./test/integration -run '^TestAutomaticCommentRepairIsolatedMySQL$' -v -count=1
```

该测试仅修改、删除自行创建的随机命名临时数据库。

## 导出与恢复边界

- 同步 SQL：原始计划，可能包含后来失败或未执行的语句；不能直接当作“剩余 SQL”。
- 同步前结构：涉及目标表的原始建表语句、是否原本存在及 SHA256。
- 报告 JSON：完整任务明细，不含连接密码。
- 恢复参考 SQL：规划器可提供的反向 DDL，按反向顺序导出，必须人工审阅；部分失败时尤其不能直接执行整份反向脚本。

**结构快照不含数据，无法恢复被 DROP 的表/字段数据，也不能恢复类型收缩造成的数据损失。**

桌面通过系统保存对话框导出；具有可用后端绑定的浏览器运行环境使用文件下载。
